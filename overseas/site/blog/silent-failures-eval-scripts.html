8 Silent Failures That Make Your Eval Number Meaningless

Static analysis notes from auditing LLM / agent evaluation scripts · Zhu Meiyan · CC BY 4.0 · evalguard

An evaluation script that prints ACCURACY 0.87 has told you almost nothing. Not because 0.87 is low or high — but because a script can produce a confident-looking number while every step underneath it is broken. The failure modes below are not hypothetical. Each one was found by static analysis on real code, including on our own checker, where several of them hid for multiple releases.

The dangerous property they share: the output looks identical whether the check is working or not.

---

1. A metric with no baseline

BLOCKER 
# reports accuracy, never asks "better than what?"
acc = hits / len(cases)
print(f"ACCURACY {acc:.2f}")

With no random baseline and no majority-class baseline, 0.87 is uninterpretable. On a dataset with 85% single-class prevalence, 0.87 is worse than a constant predictor. This is the single most common defect we see.

Fix: compute the random and majority baselines in the same script and print all three. If your method does not clearly beat both, the number is noise.

Measured: on a 40-case RAG harness, this was one of two blocker-level findings. The script's author believed 0.87 was good. Without a baseline, that question cannot be answered from the script.

2. A bare except that turns failures into clean data

BLOCKER 
for c in cases:
    try:
        out = model.query(c.prompt)
    except Exception:
        pass          # ← real errors become silent non-hits
    if matches(out, c.expected):
        hits += 1

Every API timeout, every rate-limit, every parse crash gets counted as "model got it wrong". Your eval is now measuring your infrastructure's reliability and reporting it as model capability. 40 cases, 6 silent failures, and you report 0.85 instead of 1.0.

Fix: count failures separately and fail loudly if the failure rate exceeds a threshold.

failures = 0
for c in cases:
    try:
        out = model.query(c.prompt)
    except Exception as e:
        failures += 1
        continue
    ...
assert failures / len(cases) < 0.02, f"{failures} queries failed — eval is invalid"

3. An external channel that was never re-tested

BLOCKER 
resp = requests.get(url)      # no timeout, no status check, no retry
data = resp.json()

If the endpoint returns a 403 HTML error page, resp.json() raises and — combined with #2 — your eval silently shrinks. If it returns 200 with an unexpected schema, your eval quietly measures nothing.

Our own rule for this was dead for two releases. The scanner joined source tokens with spaces, so requests.get became requests . get — and the substring test for a remote call never matched anything real. The rule reported "clean" on every file. A rule that never fires and a rule that never needs to fire produce identical output. After the fix, it fired 35 times on our own repository — the highest count of any blocker.

4. A denominator with no guard

WARN 
precision = tp / (tp + fp)     # ZeroDivisionError when fp == tp == 0
recall    = hits / len(cases)  # crashes on an empty split

Empty splits happen: a filter that matches nothing, a shard with no positive examples, a subset that got renamed. Note that len(x) is not a denominator guard — len() can legitimately be 0.

5. Measuring recall on the material you built the detector from

BLOCKER

If the failure cases in your eval set are the same cases you used to tune the detector, the recall number is circular. This is the most intellectually damaging failure on the list, because unlike the others it produces a number that is high, and high numbers don't get questioned.

Fix: hold out the tuning cases. Print which set the metric was computed on.

6. An assertion that can never fail

WARN

We hit this one in our own experiments, repeatedly, in three different disguises:

  • A contact detector summing 64 tactile cells (~50 N) against a > 1.0 threshold — always true. 39 true / 0 false.
  • A direction test asking "did this step get closer?" in a loop where error decreases monotonically — 135 true, 0 false.
  • A presence test using entropy, where a blank screen and a white screen both score 0.000 — the feature cannot distinguish the two states.
A check that can only ever return true is not a check; it is a comment that runs. Before trusting any assertion, force it to produce a false result on purpose. If you cannot construct an input that makes it fail, it is not testing anything.

7. Comments silently satisfying the check

WARN

This one bit us three times across three releases. A fixture file contained the comment # ... with no hash. The scanner read raw source, saw the substring hash, and concluded the guard was present.

Fix: never match against raw source. Strip comments and string literals first — an AST walk is the reliable way.

The same failure in reverse is just as common: "val" is a substring of "pvals", "ci" is a substring of "scipy", and ".get(" matches requests.get(. Substring matching on source text produces both false positives and false negatives, and neither is visible in the output.

8. Keyword matching standing in for semantics

WARN

We audited a public three-axis classifier whose core test is if keyword.lower() in text. Perturbation results:

PerturbationCoordinate changed
Append a trailing period0 / 29
Remove whitespace0 / 29
Reorder sentences0 / 29
Append an unrelated sentence0 / 29
Replace one word with a synonym6 / 20 (30%)
Replace three words10 / 20 (50%)

Every surface perturbation: zero change. One semantic substitution: 30% of cases flip. The classifier is robust to exactly the things that don't matter and fragile to the one thing that does.

The asymmetry is also diagnostic: the most abstract axis was the most fragile (77.8% → 50.0%), because it relied on architecture words with wide synonym space, while the axis keyed to concrete action verbs barely moved.

---

The general pattern

All eight share one structure:

The failure is invisible in the output channel you are watching.
  • No baseline → you can't tell good from bad (the number is printed either way)
  • Bare except → real errors and correct non-answers look the same
  • Dead rule → "clean" means "checked" or "never ran", indistinguishably
  • Saturated assertion → 39/0 looks like success, not like a broken test
  • Substring match → passes on a comment, fails on a synonym

So the discipline is not "add more checks". It is: for every check, demonstrate an input that makes it fail. A check with no reachable false case is decoration.
