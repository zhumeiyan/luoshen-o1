The failure mode this catches

Your eval script runs. It exits 0. It prints a table. The numbers look plausible. Six weeks later someone discovers the baseline was never actually computed, or except: pass swallowed every real error, or recall was measured on the same corpus the model was tuned on.

Nothing crashed. That's exactly why nobody noticed. evalguard reads the source and flags those patterns before you trust the result.

Measured, not claimed

We ran the rules against real, professionally written evaluation code — 55 files from 23 open-source projects (lm-evaluation-harness, HELM, BIG-bench, SWE-bench, inspect_ai, olmes, ragas, DeepEval, MLflow, unitxt, TruLens, FastChat, Haystack, Phoenix, promptbench, ...). Then we read every single finding at the line it pointed to and asked: would a reviewer looking at this line agree?

Rule classFindings confirmedStatus
Syntax — unguarded division, bare except, silent handler in a scoring loop18 of 20ships
Methodology — no baseline, no held-out set, no spread, no order swap1 of 55switched off

The second row is the interesting one. Those rules were our flagship — "you reported accuracy with no random baseline" is the headline example on this page's predecessor. On real code 54 of 55 were false: they fire on metric libraries and framework plumbing, where the thing they accuse you of omitting was never supposed to exist. The claim was literally true and practically useless.

So we turned them off and shipped three rules instead of twenty-six. The precision of what remains is 90% (Wilson 95% CI 0.70–0.97), measured on files from projects we had never scanned before.

What we are bad at, stated plainly — with the numbers from this week: we tested the shipped rules on code that is not eval code at all, to check whether the silence was a domain problem. It wasn't.

Corpus (never scanned before)Findings per 100 KBFiles it said nothing about
7 mature libraries — requests, flask, scrapy, celery, yt-dlp, fastapi, httpie0.913 of 14
8 low-star projects (5–67 stars)1.613 of 15

We then removed every guard check and re-ran, to find out whether we had over-pruned. Un-pruned, the low-star corpus produced 29 findings of which 1 was real — 3.4%. The rest were except Exception with a logger, typed retries like except (OSError, ValueError): continue, and handlers carrying # noqa: BLE001 with a written reason. Those are correct code, not defects. So the pruning was necessary, not excessive: the silence is real.

Consequence: the paid tiers are paused. A tool that speaks once per 100 KB — and is wrong a third of the time when it does — is not something we will take money for. The free tier stays up. If you maintain a mature library this tool will probably tell you nothing, and we would rather say that here than in a refund email.

Where the rules come from

Each rule traces back to a numbered entry in a 368-item failure catalogue built from ~100 experiments — mostly failures that actually happened to us, recorded with the measured number that exposed them.

Example: canon entry #23 is “a silent failure that produces a clean output is indistinguishable from success unless you check”. That single entry has now caused bugs in evalguard itself three separate times — including once where a rule was muted by a comment in the very file it was scanning. It's in the changelog.

A real report (from a real request)

The user pasted a RAG eval harness that printed ACCURACY 0.87 and asked whether the number meant anything. evalguard's reply:

evalguard report (current build) · 2 findings

| sev  | rule   | line | what                                     |
|------|--------|------|------------------------------------------|
| WARN | EG005  | 9    | hits / len(cases) — denominator unguarded|
| WARN | EG006  | 17   | bare/silent except                       |

0 blocker · 2 warn

The bare except means some of those 40 cases may have failed silently and still counted as non-hits — so the 0.87 is computed over an unknown denominator. That part the tool still gets right.

An earlier build of this page also reported "no random baseline" and "no positive control" on this same script. Those two rules are switched off now: run against professional evaluation code they were right 1 time in 55. We kept the honest part of the answer and dropped the part that was mostly noise.

FAQ

Does this work with my framework?

It reads Python source. It doesn't care whether you use pytest, lm-evaluation-harness, a bespoke notebook, or a shell wrapper — if the evaluation logic is in Python, it scans it.

Will it flood my CI with warnings?

On correctly-written code it produced zero output. The free tier is deliberately the four highest-frequency real defects, precisely so it stays quiet on everything else.

Is the catalogue actually verified?

The entries are ours, from our own experiments. The taxonomy has not been independently validated by human annotators, and we say so in the package. What's verified is the behaviour of the tool: the detection and false-positive numbers above are reproducible from the fixtures shipped with it.
