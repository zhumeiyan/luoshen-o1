# 131 · 为什么精确率上不去——定位"有没有"和"对不对"是两件事

> 判据蓝本声明：本文所有 TP/FP 判定由我一人完成，无独立复核者。
> 因此本文同时给出**严格**与**宽松**两套判定，结论必须在两套下都稳健才予主张。

---

## 0. 结论先给

**17 条真实语料发现，严格精确率 1/17 = 5.9%，宽松 10/17 = 58.8%。**
**两套标准都未达 60% 上架门槛。v0.4.0 不挂付款链接。**

加 G-ROLE（示例文件降级）后：15 条可操作，strict 6.7%、loose 66.7%。
**宽松达标、严格不达标——闸门取严格，FAIL。**

---

## 1. 语料是真的，判定是我做的

27 个文件来自 9 个权威评测框架的真实源码：`lm-evaluation-harness`、
`inspect_ai`、`olmes`、`BIG-bench`、`simple-evals`、`helm`、`SWE-bench`、
`lighteval`、`openai/evals`。上一轮（129/130）用的是同一批。

全部 17 条的判定与理由留在 `labels131.json`，每行含：
`strict` / `loose` / `anchor_ok` / 源码原文 / 判定理由。可逐条复核。

**两套标准的定义：**

| | 判 TP 的条件 |
|---|---|
| **strict** | 评审者看到"规则 + 行号 + 该行源码"会认为这行确实有这个问题 |
| **loose** | 规则的指控在文件层面成立（忽略钉在哪一行） |

为什么必须有两套：**我是唯一裁判。** 只报一套数字，我就有可能是在用
判定松紧制造想要的结果。若结论只在某一套下成立，就不予主张。

**结果：两套都不达标。** 这个结论对裁判松紧稳健。

---

## 2. 三个候选成因，只有一个真正分离

### 成因 1 · 文件角色 —— 干净，但只能去掉 2 条

```
example     n=2   strict 0/2  0.0%   loose 0/2  0.0%   ← 双标准一致全假
script      n=4   strict 0/4  0.0%   loose 3/4 75.0%
harness     n=4   strict 1/4 25.0%   loose 3/4 75.0%
metric-lib  n=7   strict 0/7  0.0%   loose 4/7 57.1%
```

`examples/`、`docs/` 下的文件，**两种标准下没有一条是真的**。样本只有 2 条，
但两套标准完全一致，方向可信。已据此加 G-ROLE：此类文件的发现降级为 `info`
（保留、计数、不删除，降级可审计）。

### 成因 2 · 锚点是否就是被指控的构造 —— **唯一强分离因子**

```
anchor 正确      6/17 = 35.3%
  其中 loose 精确率   5/6  = 83.3%
anchor 错误     11/17 = 64.7%
  其中 loose 精确率   5/11 = 45.5%
```

**钉对位置的那 6 条，宽松精确率 83.3%，已超门槛；钉错的 11 条只有 45.5%。**

这是本轮最重要的发现：**130 解决的是"有没有行号"（line≤1 从 86.4% 降到 0%），
131 暴露的是"行号对不对"——只有 35.3% 钉在被指控的构造上。**

**定位存在 ≠ 定位正确。** 上一轮我把它当成同一个问题了。

典型：`olmes` 的 EGP06 钉在 `logger.info(f"GPU memory:\n{gpu_memory}")`。
这是 130 就诊断过的"`_metric_line` 返回文件首个 emit 调用"，**本轮仍在，没修好**。

### 成因 3 · 缺失型规则 vs 存在型规则 —— 样本不足，不作主张

```
absence   n=15   strict 1/15  6.7%   loose 9/15 60.0%
presence  n=2    strict 0/2   0.0%   loose 1/2  50.0%
```

直觉上"缺失型规则无法区分『忘了写』和『这层不该写』"很有说服力，
但 **presence 只有 2 条**，做任何统计检验都无意义。
**此处只作定性观察，不主张因果。**

## 3. 修 A 坏 B，两笔都记

**采纳**：G-ROLE 抑制 `examples/`、`docs/`。17→15，loose 58.8%→66.7%。

**但严格标准下只从 5.9% 动到 6.7%，几乎没变。**
也就是说：**这个修复只在"忽略行号"的标准下让它过线，而那正是让 v0.3.0
以 11% 精确率上架的标准。我不接受它。**

**否决**：顺带抑制 `scripts/`。理由不是感觉，是数字——
它在宽松标准下移除 2 TP + 2 FP，**净零**，且会删掉第 16 条
（`requests.get(image_url)`），那是 17 条里**唯一钉对外部调用本身**的发现。

```
采纳 examples/ 过滤   17→15   loose 66.7%
否决 scripts/  过滤   17→11   loose 63.6%  ← 更低，且删掉唯一钉对的外部调用
```

**"过滤更多"不等于"过滤更好"。** 两个修复我都先量了再决定。

## 5. 本轮的错误

1. **漏判一条**：首次 dump 出 17 条，我写成 16 条判定，漏了
   `helm` 的 EGP06（L213，`correct_answer = choice  # type: ignore`）。
   补上后分母从 16 变 17，所有百分比都要重算。**差点交一份分母错的报告。**

2. **CI 匹配字符串写反**：我统计 `"demoted (demo file)"`，而降级条写的是
   `"demo file — demoted to info"`。结果统计到的是 EG000 审计条（6 条），
   真正的降级条是 0 条。**计数看起来在跑，量的是别的量。**

3. **降级后仍计入发现**：降级条保留 `severity=info`，CI 一开始仍把它们算作
   finding，改进被自己的计数口径吃掉。改成只统计非 info。

4. **ioctl 在这台机器上返回全 0**：`FBIOGET_VSCREENINFO` 得到
   `0x0 bpp=0`。127 那次我凭印象写 1920×1080 直接 `OSError`。
   本轮改用 `/sys/class/graphics/fb0/{virtual_size,bits_per_pixel}`
   才拿到 1024×768×32。**同一个量要有两条独立探测路径，并记录哪条是死的。**

5. **OCR 首轮全是乱码**：深色底 + PIL 默认位图字体，19 行只认出 1 行。
   改白底黑字 + DejaVuSansMono 22pt 后 19 行读出 18 行。

## 6. 上屏自检

渲染 → 写 `/dev/fb0` → 回读同字节数：

```
wrote 3145728  read back 3145728  identical=True
render sha 2097c4caf483 == capture sha 2097c4caf483
TOKEN K3N7QW  ← OCR 正确读出
19 行读出 18 行
```

最后一行 `VERDICT DO NOT SHIP` 被 OCR 读成 `VWEDNTCT NO NOT CHTD`
（V/W、S/H 混淆，082 起就有的老问题）。
**我没有为了让 OCR 通过而改写这句**——它是本轮的核心结论。

## 7. 边界，不扩大

- **裁判只有我一人**，无独立复核者。双标准敏感性分析是对冲，不是替代。
- **17 条样本太小**，分层统计（尤其 example 层 n=2）只作方向，不作结论。
- **27 个文件 ≠ 全部评测框架**。未覆盖的框架上表现未知。
- **缺失型 15 : 存在型 2**，无法对规则类型做统计检验，第 2 节已声明不主张。
- **未接引擎**：本轮是工程审计，不主张任何关于存活结构的结论。
- **本轮没解决根本问题**：锚点准确性 35.3% 是最大瓶颈，已知未修。

再到该类型节点上取行号"**——而不是现在这样"先找一处，再钉上去"。

在此之前：**不上架，不挂付款链接。** 会乱叫的 linter 没人用，
这句话是我自己写在产品页上的。
