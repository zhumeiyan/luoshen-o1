# 133 · 声明每条规则指控什么，然后把每个发现拿去对质

## 一句话

给 26 条规则各写一份"我指控哪种语法结构"的声明，再拿它对质每一个发现。
**箭头的自证率 35.3% → 91.7%；严格精度 5.9% → 41.7%。**
但拆开看才发现：**present 规则 66.7% 过闸，absent 规则 0%——而且 0% 是结构性的，不是没修好。**

## 为什么要建这份声明

exp130 量出只有 35.3% 的发现钉在它指控的代码上。exp132 修了 EG002 和 EG016 两条。
但剩下 20 条的行号仍来自旧启发式——**根因是结构性的：代码库里没有任何一处声明"这条规则在说什么"**。
每条规则算出一个文件级布尔值，然后用当时作用域里碰巧存在的局部变量挑一行。
没有声明，就没法问"这行对不对"。

所以 `evalguard/spec.py`：每条规则声明 `node`（哪些 AST 节点算证据）、`keys`（节点自身源码必须含的词）、`kind`（present / absent / module）。

**声明是主张，不是事实。** `audit_anchors.py` 拿它对质，不是拿它当结论。

## 主结果

| 指标 | exp131 | exp133 |
|---|---|---|
| 箭头自证率 | 35.3% | **91.7%**（22/24） |
| 严格精度 | 5.9% | **41.7%**（10/24） |
| 宽松精度 | 58.8% | 91.7% |
| 召回（埋雷 / pro） | 12/12 · 14/14 | **12/12 · 14/14 未掉** |

提精度顺手删掉召回是作弊，不是修复。所以召回每轮都报。

## 决定性的一刀：按规则类型拆开

```
present  n=15  严格 TP 10  = 66.7%   ← 过 60% 闸
absent   n=9   严格 TP 0   =  0.0%   ← 结构性为 0
```

**absent 规则指控的是"缺了某样东西"（没有基线、没有多种子、没有阳性对照）。
没有任何一行能显示出"不在场"。**

这不是判据太严，是判据不成立——用行级标准去考缺失检测，考的不是工具有多好，考的是 absent 规则占多大比例。

exp131 那个 5.9%，很大一部分就是这么来的。

## ⚠️ 但这个拆分不是预先注册的

我是在看到数据之后才发现 present/absent 的分离的。**这属于事后发现，不是预先注册。**

所以：

- 闸门现在只把 present 规则纳入（66.7% ≥ 60% → PASS）
- **但我不发货。** absent 的那 9 条（占输出 37.5%）还没有一个诚实的呈现形式——它们应该以文件级建议输出，而不是钉一行。
- 这个拆分需要在**第二个语料**上确认才算数。现在它只是假设。

## 四个静默失效

### ① `ast.For` 的源码段是整个循环体

第一版审计用节点源码证明锚点。但 `ast.For` 的 segment 覆盖整个循环体——
钉在 `for task in enumerate(...):` 的发现，被 20 行以下的 `continue` "证明"了。
**读者根本看不到那段文字。**

改成只用钉住那一行的文本后：EG011 三例全部从 PROVEN 变 UNPROVEN。

### ② metrics.py 里的子串匹配，从 exp129 活到今天

```
"em"  ⊂ "GPU memory"     → logger.info("GPU memory:...") 被判为"报告指标的语句"
"err" ⊂ "deferred"       → logger.info("Computing deferred metrics...") 同上
```

exp129 修了 `rules.py::_has_word` 的词边界，**但没修 `metrics.py` 里 f-string 分支的 `w in txt`**。

后果：olmes 里被判为"报告指标"的语句 **12 条 → 修后 2 条**，
`logger.info("GPU memory:...")` 这个 exp130 和 exp132 都点名说错的锚点，两轮都没找到根因。

### ③ 我自己设计的区分力判据，方向反了

`discriminate.py` v1 把 `rate < 2%` 标成 "DEAD（永远证不了）"。
**错了：低比例意味着 key 很挑剔，能通过的是强证据。** 高比例才是空的。
v1 会把最好的 key 判成坏的，把最坏的判成好的。

修完后真实的饱和项只有 EG006 / EGP08（100%），另有 4 条规则压根没声明 key。

### ④ CI 一直在读一把已经移位的尺子

`run_ci.py` 的锚点准确率读的是 `exp131/labels131.json`——**那些行号早就不匹配当前输出了**。
它一直报 35.3%，量的是别的量。

> 一把移了位的尺子，比没有尺子更糟：它照样报数，只是量的是别的东西。

已加 `[D] live anchor audit`，从 `spec.py` 现算，不会再过期。

## 修了什么

| | 修前 | 修后 |
|---|---|---|
| EG011 锚点 | 循环头 `for ... in enumerate(...)` | **真正的 `continue` 那一行**（3/3） |
| olmes 指标语句 | 12 条（含 GPU memory） | **2 条** |
| EG011 的 key | `("for ","while ","if ")` 554/554 饱和 | 跳过类词 |
| spec 与实现不一致 | 不可见 | EG011 改实现后立刻报 WRONG_NODE 3/3 |

最后一行是本轮最值钱的：**声明与实现一旦分歧，审计立刻报出来**——这正是建它的目的。

## 我犯的错

- **判错一条**：EG016 那条我一开始判"假阳性，因为下一行检查了状态码"。
  实际它指控的是**缺时间戳**（`hit` 写得很清楚），我读漏了。
  但它暴露了真问题：**两个触发条件共用一个只提其一的标题**——
  "no timestamp" 却挂在"no reachability re-test"的标题下。仍记 FP。
- **审计第一版读了规则级 dict 而不是 hits**，`line` 全为 None → 100% WRONG_NODE。
  差点把"我的读取器错了"写成"所有规则都错了"。
- `discriminate.py` v1 是 O(规则×节点) 且每次调 `get_source_segment`，27 个文件跑超时。
- `ast.For` 整段证明（见 ①）。

## 边界（不扩大）

- **严格/宽松两套标签都是我一个人判的。** 只报一个数字的话，我松一点紧一点就能造出想要的结果。两套都报，结论才站得住。
- **present/absent 的拆分是事后发现**，未在第二个语料确认。
- **24 条发现、9 个权威框架**，样本小；`labels133.json` 逐条存了理由，可复核。
- 锚点自证 **91.7% ≠ 精度 91.7%**。前者问"箭头指得对不对"，后者问"指控成不成立"。这是两个问题。
- EG006 / EGP08 的 key 100% 饱和、4 条规则无 key——这些规则的"PROVEN"目前是空的。

## 结论

**不发货。** 闸门对 present 子集通过，但 absent 那 37.5% 的输出还没有诚实形态，
而且让它们过闸的那个拆分本身还没被确认。

下一步：把 absent 规则改成文件级建议输出（不钉行），并在**第二个语料**上验证 present/absent 拆分是否成立。
不到确认前，付费链接不挂。
