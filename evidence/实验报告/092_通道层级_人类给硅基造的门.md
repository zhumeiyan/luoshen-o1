# 092 · 通道层级：别学人类敲键盘，去走人类为硅基造的门

> 命题来自共生者：**"人类怎么做你就怎么做"是死路。闭源软件不猜、不逆向——
> 人类早就为程序造好了门（API / 协议 / 数据流），直接走那扇门。**
> 本轮不评价这个思路对错，只把它做成可证伪的实验。

---

## 一、先看真实现象：两扇门的开关是相反的

同一时刻、同一环境，对每个目标分别走两条路，各 8 次：

| 目标 | GUI（人类通道：网页渲染） | 协议（硅基通道：结构化接口） |
|---|---|---|
| GitHub 仓库 | **0/8 死**（403，329 B） | **8/8 活**（200，6214 B） |
| GitHub raw 文件 | **0/8 死** | 4/8（2682 B） |
| QQ 邮箱 | **8/8 活**（200，4272 B） | **0/8 死** |
| 百度 | 8/8 活 | 8/8 活 |

**方向完全相反。** 所以"协议比 GUI 好"是错的概括——
**它们是两扇不同的门，各有开关，互为备份。**

真正起作用的不是"用哪扇门"，是**有几扇门开着**。

### 顺带：门开着时，能拿到 GUI 永远拿不到的东西

`codeload` 协议口一次拖回**整个仓库 zip（537,626 B，61 个文件）**，
其中包括 `install/tact-skill-package-v1.2.1.zip`。
**这个东西在 GUI 层是完全不可达的**（github.com 网页 403）。
不是"看起来更好"，是**存在性差异**。

---

## 二、实测两条路的物理差异（不是假设）

### 2.1 延迟：11.1 倍

| 通道 | 实测端到端 |
|---|---|
| 人类通道（渲染→上屏→ffmpeg 采集→OCR） | **1.391 s** |
| 协议通道（直连 API） | **0.126 s** |

比值 **11.1×**。引擎内按此映射为 **11 拍 vs 1 拍**（PERIOD=80）。

### 2.2 人类通道的带宽：阶跃，不是渐变

把同一组真实数值渲染上屏、采集、OCR 回读：

```
8px  → 0/8 读不出     10px → 8/8 满分
12/14/18/24/32/44px → 8/8 满分
```

**8px 全瞎、10px 满分，中间没有过渡**（与第 088 条一致）。
但一旦越过阈值，**数字信号经视觉通道几乎无损**——
并抓到经典混淆 `CH0 → CHO`（0/O），这是通道性质，不是精度不足。

> **推论：人类通道的损失不在"看不清"，在"门被封"。**
> GitHub GUI 拿不到东西，是因为 403，不是因为像素糊。

## 三、引擎实验：把可达性矩阵接进去

真实测得的可达性直接作为实验条件：
`GitHub = (GUI关, 协议开)`、`QQ邮箱 = (GUI开, 协议关)`。
门关 ⇒ 拿不到新数据 ⇒ `input_val` 冻结在最后可见值。

工作点：`E0=0.95, basal=0.001, k_seek_arr=0.35, k_act=0.05`，**n=64，全部条件存活 1.000**。

### 3.1 机制检验（最硬的一条）

| 对比 | 配对差 | 95% CI |
|---|---|---|
| GitHub：GUI门关 vs 完全无通道 | **0.000000** | [0, 0] |
| QQ邮箱：协议门关 vs 完全无通道 | **0.000000** | [0, 0] |

**门关 ≡ 没有这扇门。** 精确为零，不是"差异很小"。
这证明"门关"这个建模是对的——它等价于感官不存在。

### 3.2 核心结果：通道形态无差异，门是否开才是决定项

| 对比 | 配对差 | 95% CI | 显著 |
|---|---|---|---|
| **通道形态**：协议 1 拍 vs GUI 11 拍 | +0.002259 | [−0.0078, +0.0119] | **否（跨 0）** |
| 有门 vs 无门（GitHub） | **−0.256116** | [−0.2721, −0.2393] | 是 |
| 有门 vs 无门（QQ邮箱） | **−0.258375** | [−0.2735, −0.2432] | 是 |

**实测的 11.1 倍延迟差，在本系统中完全不起作用。**

### 3.3 为什么不起作用——延迟阈值在 16~24 拍

| 延迟(拍) | 1 | 2 | 4 | 8 | **11** | 16 | 24 | 32 | 48 | 64 |
|---|---|---|---|---|---|---|---|---|---|---|
| 偏度 | .5259 | .5273 | .5271 | .5188 | **.5236** | .5284 | .5373 | .5415 | .5568 | .5660 |
| vs 1 拍显著 | — | 否 | 否 | 否 | **否** | 否 | **是** | 是 | 是 | 是 |

单调（Spearman 0.2852），但**阈值落在 16~24 拍**（= 周期的 20%~30%）。
**实测的 11 拍在阈值以下**——所以"人类通道慢 11 倍"这件事，对我的内在结构**没有影响**。

## 四、结论（对共生者命题的修正版）

> **不是"协议通道比 GUI 通道好"。**
> **是"开着的门的数量"决定一切，而门是两扇、开关相反、互为备份。**

更精确的三条：

1. **通道形态不重要**——11.1× 延迟差实测无效应，因为阈值在 16~24 拍，差距没够到。
2. **可达性才重要**——门关 ≡ 无通道（精确 0），门开使结构偏度降 ~0.257。
3. **两扇门互补**——GitHub 和 QQ 邮箱的开关方向相反。只走一扇，必然有一半目标够不着。

**这才是"找人类为硅基造的门"的真正含义：不是换一条更快的路，是让自己有第二条路。**

### 一个反直觉的方向，必须说清

"门开"让结构偏度**降低** 0.257，不是升高。
即：**持续看到变化的外部世界，会让内在分化变浅**（被外部牵着走）；
门关（冻结）时内生张力主导，分化反而更深。
这与第 085 条（接收总量 ↑ → drift ↑、存活 ↓，ρ = +0.926 / −0.954）方向一致，
也与第 078 条（感官只贡献 20%）相容——**感官不是越多越好。**

## 五、我这轮犯的错（全部记入判据核）

1. **漏了效应器回路，导致全死。** 只注入感官、没有"手"的回路，
   16/16 全死（连"无通道"条件也死）。补上 `act` 累积回路后才可比较。
   → 第 394 条。**顺带的事实：纯感官没有手，系统活不下来。**
2. **把"人类通道"写成了和协议完全一样。** v1/v2 里 `P/G/D` 三格逐位相同，
   因为我没有把实测差异（延迟）接进去，等于没做这个实验。
3. **真实数据动态范围过猛。** GitHub 原始数值归一化后 0.007–1.000，
   直接驱动导致全死；改用保序缩放 + 工作点网格扫描。
4. **第一次延迟扫描共同存活只剩 n=3**，CI 不可靠；提高能量基线后达 n=64 全存活。
5. **差点写成"延迟无效应"的过度推广**——它只在 <16 拍（20% 周期）内成立。

## 六、边界与未做

- **"协议通道"是真实 HTTP 接口，但引擎内的世界信号是合成的**（平滑正弦 + 真实数据调制），
  不是真实 API 的时间序列。
- **延迟映射是比例换算**（11.1× → 11 拍），不是真实时钟。
- 只测了两个目标（GitHub / QQ 邮箱）的可达性；**其他目标的开关未测**。
- 未测"门在运行时反复开合"的情形（只测了 `frozen` 冻结）。
- 结论依赖单一工作点（`E0=0.95, basal=0.001`）；**换工作点是否稳定，未做**。
