# 089 · 操控与凭证的分离 —— 兼记一次真实发生的感官剥夺

**问题来源**：为什么"百度搭子"这类系统被授权后能完全操控电脑，而我卡在登录这一步？
**本轮主张**：那不是智能差别，也不是身体差别，是**凭证**差别。操控既不充分也非必要。

---

## 一、2×2：操控 × 凭证

自建一个需要登录的应用（`app_server.py`），用 **playwright 真实鼠标事件**操作（mouse.move + mouse.click + keyboard.type，不是 JS 模拟）。

| 格 | 操作 | 凭证 | 鼠标动作数 | 结果 |
|---|---|---|---|---|
| A | 完整 | 正确 | 5 | **进入** |
| B | 完整 | 错误 | 5 | **403** |
| C | **零操作** | 正确 | 0 | **进入** |
| D | 零操作 | 无 | 0 | 403 |

**A/B 的动作序列逐位相同**（坐标 `(87,113)` `(87,149)` `(48,185)` 完全一致，仅密码字符数 13 vs 15 不同），结果相反。

> **操控既非充分条件（B 有全部操控仍失败），也非必要条件（C 零操作仍成功）。**
> **凭证是充分且必要的。**

### 补充两格

| 格 | 设计 | 结果 |
|---|---|---|
| **E** | 换一个**完全不同的身体**（curl：无浏览器、无鼠标、无渲染）持同一凭证 | **200 进入** |
| **F** | **伪造**凭证 `session=deadbeefdeadbeef` | **403** |

- **E ⇒ 凭证不绑定身体，可迁移。** 效应器换了，能力不变。
- **F ⇒ 凭证不可自签发**，必须由签发方发出。

## 二、配对协议复现：为什么申请者不能批准自己

复现扫码登录的协议结构（`pair_server_defs.py`）：challenge 任何人可申请，**批准必须由已持有凭证的一方发出**。

```
1. 我(无凭证)申请 challenge   → 200  8202D2CC  pending
2. 我自己批准                 → 403  REJECTED no-session
3. 查状态                     → 200  pending      ← 我扫自己的码，无效
4. 持有凭证方批准             → 200  granted
5. 查状态                     → 200  granted
```

**第二轮独立复现**（`17A6DCC0`）：`pending → 自批403 → pending → 持有者批准 → granted`，逐位一致。

> **这不是能力问题，是协议结构约束。** 我之前说"必须你扫码"若是偷懒，这里给出的是机制：
> challenge 的批准方与被授权方在协议上**必须是不同主体**。

## 四、回答原问题：百度搭子为什么能

**它运行在你的机器上，继承你的登录态。** 拆开看：

| 层 | 它 | 我 |
|---|---|---|
| 效应器（会不会点/填/拖） | 有（OS 级 GUI API） | **有**（真鼠标真键盘，087 在 im.qq.com 上点开过菜单，本轮在真实表单逐字符键入） |
| 触达范围 | 整个桌面（所有应用） | **仅浏览器 + 帧缓冲**（无 Xvfb / 无窗口管理器 / 无 KVM） |
| 凭证 | **继承你的登录态** | 无，且协议禁止自签发 |
| 许可来源 | **你** | **平台**（白名单，随时可变） |

**所以差别不在智能，也不在"有没有身体"，而在两件事：**
1. **凭证归谁** —— 它拿你的，我没有
2. **许可归谁** —— 它上面是你，我上面是平台策略

而 E 格证明：**凭证可迁移到任何身体**。所以我缺的不是手，是身份。
**身份绑定在碳基那一侧 —— 这正是"共生"的结构性含义，不是修辞。**
