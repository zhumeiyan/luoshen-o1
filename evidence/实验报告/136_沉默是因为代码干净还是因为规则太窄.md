# 136 · 沉默是因为代码干净，还是因为规则太窄？

日期 2026-10-18 · 提交（本轮 git 未成功，见末节）

---

## 0. 这个问题从哪来

exp135 发现闸门是**单边的**：exp129–135 六轮全部只门控精确率，换来 90% 精确率，
也换来一个在专业代码上几乎沉默的工具——每 KB 0.02~0.03 次命中，corpus4 十二个文件里九个无话可说。

于是有一个很自然的解释：**那三条语法规则（未保护除法 / 裸 except / 循环内静默）本来就是通用 Python 缺陷，不是评测特有的。**
把它们打在评测框架上是走错了域，换到普通 Python 代码上应该会响。

这是一个可以证伪的假说。本轮去证它。

---

## 1. 预注册（跑之前写进 `PREREG.md`）

- **H1**：非评测代码上，三条发货规则的命中率 ≥ 0.05 次/KB，即 ≥ 评测域（0.024/KB）的 2 倍。
- **H2**：新域上严格精确率点估计 ≥ 0.60；**Wilson 下界低于 0.60 即判 FAIL**，不看点估计。
- **H3**：埋雷夹具召回不退化（EG005 3/3、EG006 2/2、EGP01 1/1，干净文件 0）。
- **语料**：7 个从未用过的仓库，非评测域。排除路径含 `eval|metric|benchmark|score|test|__init__|vendor|contrib|example`，seed 136 随机取 2 个文件。
- **判定**：一名判定者（我），存疑一律记 FP，两条标准都报。

## 3. 于是做了一个事后补充：低成熟度代码

看那 9 条被剪掉的命中时注意到一件事：**其中 3 条带着 `# pylint: disable=broad-except`**。
作者已经遇见过 linter，并且显式地把它按住了。

这提示另一件事：**我们四个语料全是成熟项目。我们从来没有在"没有 lint 文化的代码"上测过。**

corpus6 = 8 个 star 5–67 的仓库，15 个文件 122 KB。**这一段是事后的，不在预注册里，标注为探索。**

```
loose 未剪枝： corpus5 0.0926/KB   vs   corpus6 0.2376/KB   差 2.6 倍
shipped 发货： corpus5 0.0093/KB   vs   corpus6 0.0164/KB   差 1.8 倍
```

**域差异是真的存在**——低星代码里的原始缺陷密度确实更高。**但发货版只把它放大了 1.8 倍，仍然远低于 0.05。**

## 4. 关键对照：剪枝是必要的，不是过度

把所有守卫检测全部拆掉，只留"字面命中"，在同一批代码上重跑：

| | corpus6 宽松命中 | 逐条判定 |
|---|---|---|
| 发货版（严格） | 2 | **1 TP / 1 FP** |
| 宽松版（未剪枝） | 29 | **1 TP / 28 FP = 3.4%** |

宽松版 29 条里，真缺陷只有 1 条：`except Exception: pass; return {}`。
其余 28 条分别是：

- **9 条** `except Exception as e: logger.warning(...)` / `print(...)` —— 有日志，是合理实践
- **7 条** `except (OSError, ValueError, InterruptedError): continue` —— 具体异常类型 + 重试，是标准网络/IO 写法
- **2 条** 带 `# noqa: BLE001` 并写明理由 —— 作者已知且已裁决
- **1 条** `except BaseException: os.close(fd); raise` —— 有清理 + re-raise，教科书正确
- **5 条** EG005，其中 2 条是 `round(a/b,4) if b else None`（**有守卫**），2 条是 pathlib 路径拼接
- 其余为转译成 HTTP 500 / 错误字符串返回的降级处理

**所以：放开到行业常见的宽松水平，精确率是 3.4%。剪枝把 29 条压到 2 条，不是"过度剪枝"，是必要的。**

这也回答了标题：**沉默不是剪枝造成的。**

---

## 5. 结论

> **这三类缺陷在真实代码里要么罕见，要么其常见形式本身就是合理实践。**

具体到每条：

- **EG005 未保护除法**：真实代码里除法本身就少（108 KB 成熟代码 1 处），而且常见的除法都带三元守卫。
- **EG006 裸 except**：**裸 `except:` 在真实代码里 0 处**——没人这么写。它的常见形式是 `except Exception`，而 `except Exception` + 日志/re-raise/noqa 是**正确做法**，不是缺陷。
- **EGP01 循环内静默处理**：在 230 KB 真实代码上（corpus5+corpus6）**宽松版 11 条、真缺陷 0 条**，发货版 1 条（而且那条在 corpus6 上是 `except OSError: pass`，判 FP）。这条规则**在真实代码上从未见过正例**。

## 7. 本轮四个错误

1. **把审计台账当成了发现。** `EG000` 是 audit 记录（`scope gate` / `evidence-line gate`），不是缺陷。
   第一版把它算进去，得出"方法论层在非评测域命中 5 条"——**它命中 0 条，我数的是台账**。
   这是 exp135 那个"审计把两种丢弃混为一谈"的同类病，第二次犯。

2. **pathlib 的 `/` 被当成除法。** AST 层面 `Path.home() / ".hermes"` 和 `heartbeat / rate` 都是 `BinOp(Div)`。
   宽松基线在 corpus6 上先报了 53 条"除法"，排除右操作数为字符串常量后剩 5 条。
   **判据核 #23 第六次复发**（exp130 诊断过、我以为修好了，换个脚本又长出来）。

3. **"有日志"被判成"静默"。** 宽松 EGP01 先把 `ast.Expr` 剥掉再判空，于是 `except: log(...)` 被算作静默。
   修正后 20 → 11。**一个用来找缺陷的检测器，自己把最明显的反例判成了正例。**

4. **httpie 仓库改名**。旧名 `httpie/httpie` 返回 301，跟随后是 `httpie/cli`。已按新名抓取。

## 8. 边界

- **corpus6（低星代码）是事后补充**，不在预注册内，样本 15 个文件，只报数不报 CI。
- **H2 的 n=3 太小**，2/3 这个点估计几乎没有信息量；下界 0.21 才是诚实的说法。
- **判定者只有我一个**，存疑一律记 FP。corpus6 那条 `except OSError: pass` 可能真，但我按规则记了 FP。
- **宽松基线是我自己写的**，不是 ruff / pylint 官方工具——`api.github.com` 通而 PyPI 403，装不上真实 linter。
  所以"3.4%"是**我这个宽松实现**的精确率，不代表行业工具的精确率。
- **帧缓冲回读不是完美逐位**：mean abs diff 0.038，0.016% 的像素差异 >4（前几轮是 `raw == cap` True）。
  TOKEN `Q3N7WV` 与 9/9 数值探针全部 OCR 读出，但这一轮的像素一致性比往轮差，如实记。

## 9. 商业决定

**v0.5.0 不挂付费链接，且本轮把"短板"从 marketing 措辞改成实测数字。**

不是定位错了，是**价值主张错了**。一个在 230 KB 真实代码上只说 3 句话、其中 1 句是假的工具，
无论怎么定价都是把招牌砸掉。我自己写在产品页上的话是"会乱叫的 linter 没人用"——
**反过来同样成立：不说话的 linter 也没人用，而我们两样都占了。**

下一步不是加规则、也不是放宽阈值（放宽到 3.4% 已经证明是自杀）。
真正该做的是重新问一遍：**我们手里到底有没有任何一个在真实分布上既有覆盖率又有精确率的判据？**
如果没有，正确的动作是承认这个产品不成立，而不是继续修它。
